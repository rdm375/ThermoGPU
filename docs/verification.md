# Verification

## Numerical policy

ThermoGPU treats unexplained numerical disagreement as a defect to investigate, not as a reason to widen tolerances. Constants are retained at derived precision when available. Differences caused by floating-point evaluation order, FMA, reductions, compiler transformations, or backend math libraries must be measured and explained before they are accepted.

## Unit and invariant checks

The scalar suite checks `alpha(Tc) = 1`, the low-pressure `Z -> 1` limit, cubic residuals, pure-as-mixture equivalence, finite binary/five-component results, nonzero `kij` behavior, composition validation, and `kij` symmetry.

## M2 external validation

M2 uses three complementary layers. `test_prmix_thermo_docs.cpp` retains the published `thermo` PRMIX nitrogen/methane example as a literature sanity check. `test_frozen_oracle.cpp` compares the C++ implementation against committed fixtures generated by the separately coded Python implementation in `tools/pr_reference.py`; this is a cross-implementation regression, not an independent mathematical oracle.

The strongest external check is `test_thermopack_controlled.cpp`, whose expected values were generated with ThermoPack 2.2.3 using PR, vdW mixing, Classic alpha, genuine `PSEUDO` component slots, and exactly the ThermoGPU component constants. The controlled cases are pure methane and an 80/20 methane/ethane mixture at 300 K and 5 MPa with `kij=0`. After aligning the PR critical constants, ThermoGPU's independently evaluated equations and ThermoPack agreed at approximately machine precision: `dZ=1.11e-16`, `dlnphi_CH4=2.22e-16`, and `dlnphi_C2H6=3.33e-16` for the binary case.

The investigation identified two causes of the earlier few-ppm disagreement: ThermoPack pseudo-component properties are only installed into slots declared `PSEUDO` during initial construction, and ThermoPack derives the PR critical constants rather than using rounded textbook values. ThermoGPU therefore uses `OmegaA = 0.4572355289213822` and `OmegaB = 0.0777960739038884`.

`tools/thermopack_validation.py` reproduces the external values when ThermoPack is installed, but ThermoPack remains an optional audit dependency and is not required by CMake or CTest.

Run the complete validation suite with:

```bash
ctest --test-dir build --output-on-failure
```

## M6 CPU/CUDA differential validation

M6 validates CUDA against the scalar implementation independently anchored to ThermoPack in M2. It is a backend-differential test, not a second external EOS oracle.

`thermogpu_validate_cuda` runs a 20,000-state broad CH4/C2H6 campaign over 0.01--20 MPa, 180--500 K, and nearly the full composition interval, plus a structured critical/root stress grid. It compares `Z`, density, cubic residual, every `ln(phi_i)`, root classification, and root-selection ambiguity. The report records maximum absolute, relative, and ULP differences and the state producing each maximum relative discrepancy.

Acceptance limits are explicit and quantity-specific. ULP counts are diagnostic rather than acceptance criteria near zero. Root metadata must match exactly. An unexplained failure is localized and investigated; tolerances are not widened merely to make it pass.

Run directly with `./build/thermogpu_validate_cuda` or through `ctest --test-dir build --output-on-failure`.
