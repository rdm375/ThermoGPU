# Reference validation

ThermoGPU uses three deliberately different cross-checking layers.

1. `test_prmix_thermo_docs.cpp` is an **external sanity check** against published
   `thermo` PRMIX documentation values. Those values do not freeze every numerical
   input, so small differences are expected and the test deliberately uses looser
   tolerances.
2. `test_thermopack_controlled.cpp` freezes externally generated ThermoPack 2.2.3 results for controlled pure-methane and methane/ethane pseudo-component cases. ThermoPack is not a runtime dependency; `tools/thermopack_validation.py` reproduces the external values when the optional validation environment is installed.
3. `test_frozen_oracle.cpp` is the **frozen-input cross-implementation campaign**.
   Its CSV fixtures are generated by `tools/pr_reference.py`, a separate
   standard-library Python implementation that shares no ThermoGPU C++ code.
   Both sides receive the same literal `R`, `T`, `P`, component constants,
   composition, and `kij` values. This is useful for detecting implementation
   mistakes and localizing numerical divergence, but it is not claimed to be an
   independent mathematical validation because both implementations were written
   from the same Peng-Robinson specification. The controlled ThermoPack cases are the strongest third-party external anchor; the published `thermo` regression provides an additional literature check.

## Frozen campaign

The eight committed cases are selected by failure mode rather than as eight
variations of an ordinary gas state:

- `methane_low_pressure`: ideal-gas limiting behavior.
- `methane_moderate_pressure`: ordinary pure-fluid PR calculation.
- `methane_ethane_binary`: ordinary multicomponent mixing and fugacity.
- `binary_nonzero_kij`: explicit nonzero binary interaction coefficient.
- `five_component`: representative multicomponent natural-gas calculation.
- `high_pressure_five_component`: dense/high-pressure numerical stress case.
- `binary_three_root`: three-real-root cubic and deterministic vapor-root selection.
- `methane_near_critical`: near-critical numerical sensitivity.

For every case the validator compares intermediate quantities, not just final
fugacities: `alpha_i`, `a_i`, `a_i alpha_i`, `b_i`, `sum_j z_j a_ij`, `a_m`,
`b_m`, `A`, `B`, every real root, selected `Z`, density, `ln(phi_i)`, `phi_i`,
and fugacity. This is intentional: a failure should identify the first stage at
which the implementations diverge.

Run the campaign summary with:

```bash
./build/test_pr_frozen_oracle tests/reference/data
```

Print every C++/frozen-reference comparison with:

```bash
./build/test_pr_frozen_oracle tests/reference/data --verbose
```

CTest runs the same frozen campaign non-verbosely:

```bash
ctest --test-dir build -R pr_frozen_oracle --output-on-failure
```

Regenerate all committed fixtures only as an explicit developer action:

```bash
for case in \
  methane_low_pressure methane_moderate_pressure methane_ethane_binary \
  binary_nonzero_kij five_component high_pressure_five_component \
  binary_three_root methane_near_critical; do
  python3 tools/pr_reference.py "$case" "tests/reference/data/$case.csv"
done
```

Fixture regeneration is intentionally not part of CTest. An accidental change
cannot silently modify both the implementation and its expected answers in the
same test run.
